# Beyond webhook delivery. Verify financial correctness.

BachsProof is a financial correctness testing framework for applications that
use Bachs. In simple English: it sends safe test payment notifications to your
application and checks whether your application saved the right money state.
It complements Bachs' developer tools and normal test frameworks; it does not
replace them.

BachsProof is an independent, unofficial project for testing Bachs integrations. It sends controlled, synthetic payment events to your isolated application and checks the financial state your application actually commits. It does not process real payments, verify provider settlement, or certify production readiness.

## A ₦5,000 payment can still be wrong

Imagine a customer deposits **₦5,000**. In NGN, the application expects one
credit of `500_000` kobo. Two identical webhook deliveries arrive together:

```text
Delivery A reads payment status: PENDING
Delivery B reads payment status: PENDING

Delivery A credits ₦5,000
Delivery B credits ₦5,000

Expected wallet credit: ₦5,000
Actual wallet credit:   ₦10,000
```

Both deliveries can receive successful HTTP responses. The request was accepted,
but the money is wrong. BachsProof sends the test events and uses your
application-specific `verify` callback to inspect the state that was actually
saved.

## Three levels of testing

Start with the smallest level that answers your question:

| Level | What it checks | What you must provide |
| --- | --- | --- |
| Delivery only | The endpoint receives the event and returns the expected HTTP status | `provider`, `target`, and `tests` |
| Financially verified | The saved credit count, amount, currency, and payment state | The first level plus real test references and `verify` |
| Controlled concurrency | A chosen application execution point is coordinated across requests | The second level plus optional `@bachsproof/sdk` instrumentation and `checkpoint` settings |

Delivery-only is useful for checking the webhook boundary, but it cannot prove
that money was saved correctly. Most teams should make financially verified
tests their normal CI level. Add controlled concurrency only when you need to
reproduce a particular race.

## A simple reading path

If payment testing is new to you, read [Why BachsProof exists](/why-bachsproof),
then [Quickstart](/quickstart), and then [Financial verification](/testing/financial-verification).
After that, choose the scenarios and invariants that match your application.

If you already build payment systems, read [Architecture](/how-bachsproof-works/architecture),
[Execution lifecycle](/how-bachsproof-works/execution-lifecycle), and the
[Reference wallet case study](/case-studies/reference-wallet). Use the API
reference only when you need exact types and defaults.

<Note>
Financial verification requires callbacks that know your application's payment,
ledger, and wallet schema. BachsProof does not automatically understand every
database or guarantee that untested production behaviour is correct.
</Note>

<Warning>
Use only isolated test applications, test databases, and test-only webhook
secrets. Synthetic events must never be delivered to production.
</Warning>
