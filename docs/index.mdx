# Beyond webhook delivery. Verify financial correctness.

BachsProof is a financial correctness testing framework for applications integrating Bachs. It complements existing webhook testing tools by enabling developers to verify payment processing, idempotency, concurrency safety and financial integrity within their applications.

BachsProof is an independent, unofficial project for testing Bachs integrations. It sends controlled, synthetic payment events to your isolated application and checks the financial state your application actually commits. It does not process real payments, verify provider settlement, or certify production readiness.

## Four ways to test what matters

<CardGroup cols={2}>
  <Card title="Financial correctness" icon="wallet">
    Check committed credits, ledger entries, amounts, currencies, and payment
    eligibility instead of treating an HTTP success response as proof of a
    correct financial result.
  </Card>
  <Card title="Concurrency safety" icon="shuffle">
    Deliver duplicate or independent payment events concurrently and expose
    race conditions that sequential tests may never create.
  </Card>
  <Card title="Payment reliability" icon="rotate-ccw">
    Exercise retries, duplicate event identities, ordering changes, incomplete
    checkouts, failed collections, malformed payloads, and invalid signatures.
  </Card>
  <Card title="Developer-first testing" icon="code">
    Run from the `bachsproof` CLI or call the runner from Vitest, Jest, or
    another test suite using your existing application setup.
  </Card>
</CardGroup>

## A ₦5,000 payment can still be wrong

Imagine a customer deposits **₦5,000**. In NGN, the application expects one
credit of `500_000` kobo. Two identical webhook deliveries arrive together:

```text
Delivery A reads payment status: PENDING
Delivery B reads payment status: PENDING

Delivery A credits ₦5,000
Delivery B credits ₦5,000

Expected wallet credit: ₦5,000
Actual wallet credit:   ₦10,000
```

Both deliveries can receive successful HTTP responses. Delivery succeeded, but
the financial outcome is wrong. BachsProof sends the controlled test events and
uses your application-specific `verify` callback to inspect the committed state.

<Note>
Financial verification requires callbacks that know your application's payment,
ledger, and wallet schema. BachsProof does not automatically understand every
database or guarantee that untested production behaviour is correct.
</Note>

<Warning>
Use only isolated test applications, test databases, and test-only webhook
secrets. Synthetic events must never be delivered to production.
</Warning>
