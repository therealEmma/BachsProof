---
title: "Out-of-order events"
description: "Check that an older non-fulfilling event cannot replace newer success."
---

## What problem does it test?

Networks can deliver an older event after a newer one. If a successful ₦5,000
collection is followed by an older checkout expiry, the expiry must not erase
the completed financial state.

## What BachsProof sends

The adapter sends a newer eligible `collection.succeeded` first, then an older
`checkout.expired` event. They have different IDs and timestamps and normally
receive 2xx responses. The event order is intentionally different from the
timestamp order.

## What the application should do

Accept the newer successful state and ignore the older non-fulfilling state when
it would regress a completed payment. Store event time or an equivalent durable
ordering value. Arrival order alone is not enough.

## Expected outcome and failure

The application should keep one completed `500_000`-kobo NGN credit. `INV-001`
protects uniqueness and `INV-003` protects completion. The old event must not
create an unexpected credit or downgrade the payment.

```js
{
  name: "older expiry cannot undo success",
  scenario: "out-of-order-events",
  amountMinor: 500_000,
  currency: "NGN"
}
```

## Internal implementation

`createBachsScenario` in `packages/bachs/src/fixtures.ts` creates the expiry at
`now` and the success at `now + 1_000` ms, then lists the success before the
expiry. The corrected reference wallet compares event timestamps in
`processCorrected` and does not downgrade a completed payment.
