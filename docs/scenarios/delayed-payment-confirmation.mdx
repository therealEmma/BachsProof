---
title: "Delayed payment confirmation"
description: "Check that a later valid confirmation can still fulfil a payment."
---

## What is being tested?

This test sends an expiry-like event first and a valid successful collection
later. The successful event is delayed by a small, configurable amount.

## Why does it matter?

Payment systems are asynchronous. An early signal does not always settle the
payment. If the application permanently rejects the order too soon, a later
valid payment can never be fulfilled.

## What BachsProof does

BachsProof sends `checkout.expired`, waits for `delayMs` (25 ms by default),
then sends an eligible `collection.succeeded` event for the same payment. For
example:

```js
{
  scenario: "delayed-payment-confirmation",
  delayMs: 100,
  amountMinor: 500_000,
  currency: "NGN"
}
```

Run it with:

```bash
pnpm exec bachsproof test --name "delayed payment confirmation"
```

## What the application should do

Record the early state without making a later valid success impossible. If a
worker handles the webhook, `verify()` should return `pending: true` while that
work can still change the saved state.

## Pass and failure

After the successful event is processed, a pass has one `500_000`-kobo NGN
credit. No credit by the verification deadline fails `INV-003`; a duplicate
fails `INV-001`. This test covers the configured delay and observation window,
not every possible queue delay.
