---
title: "Delayed payment confirmation"
description: "Check that a later valid confirmation is not permanently rejected."
---

## What problem does it test?

An early lifecycle signal can arrive before a payment is confirmed. A later
successful collection should still fulfil the ₦5,000 payment once it is valid.
An application should not permanently mark an order unusable because it saw an
earlier expiry-like signal.

## What BachsProof sends

It sends `checkout.expired` first, then delays an eligible
`collection.succeeded` delivery. The delay defaults to 25 ms and can be set with
`delayMs`:

```js
{
  name: "delayed ₦5,000 confirmation",
  scenario: "delayed-payment-confirmation",
  delayMs: 100,
  amountMinor: 500_000,
  currency: "NGN"
}
```

## What the application should do

Record the non-fulfilling state without making a later valid success
impossible. If a worker is involved, the verifier should return `pending: true`
until the successful event has been committed.

## Expected outcome and failure

After the success is processed, the verifier should observe one
`500_000`-kobo NGN credit. Missing completion fails `INV-003`; a duplicate
fails `INV-001`. The scenario does not prove behavior beyond the configured
delay and verification deadline.

## Internal implementation

`createBachsScenario` in `packages/bachs/src/fixtures.ts` creates the two-event
ordered plan and applies `delayMs` before the successful delivery. Polling is
implemented by `verifyWithCallback` in `packages/core/src/verification.ts`. The
delay is a local test schedule, not a live provider settlement delay.
