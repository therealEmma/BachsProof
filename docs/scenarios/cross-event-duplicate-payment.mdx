---
title: "Cross-event duplicate payment"
description: "Check that two lifecycle events for one payment do not double credit."
---

## What problem does it test?

One financial payment can be described by more than one lifecycle event. A
₦5,000 deposit described by both a completed checkout and a successful
collection is still one deposit. Treating event types as separate payments can
create two credits.

## What BachsProof sends

`createBachsScenario` creates `checkout.completed` and `collection.succeeded`
events concurrently for the same reference, checkout ID, and provider payment
ID. The checkout is eligible only when it is payment mode, has
`status: "completed"`, `payment_status: "paid"`, a currency, and a charge.
Both deliveries normally expect 2xx.

## What the application should do

Match both events to the same stored payment and use a business idempotency key,
not only the event type. The application should create one credit and preserve
the provider/event records needed for reconciliation.

## Expected outcome and failure

One `500_000`-kobo NGN credit is expected. Two credits fail `INV-001` and the
wrong aggregate also fails `INV-002`; a missing credit fails `INV-003`. A wrong
amount or currency on one expected credit fails `INV-002` and possibly `INV-005`.
Configure `verify` to prove the one-credit result.

```bash
npx bachsproof test --name "cross-event duplicate payment"
```

## Internal implementation

`checkoutFixture` in `packages/bachs/src/fixtures.ts` creates the completed
checkout while the base fixture remains `collection.succeeded`. The provider
plan sets `concurrent: true`; core delivers both events and verifies the shared
reference once. This is limited to the documented event semantics represented
by the current adapter; it is not a claim that every Bachs event pair is
interchangeable.
