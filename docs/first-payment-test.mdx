Start with `sequential-duplicate-webhook`. It delivers the same eligible
payment twice, in sequence. The customer paid once, so a correct wallet should
create one credit, not two.

```js
export const tests = [
  {
    name: "sequential duplicate webhook",
    scenario: "sequential-duplicate-webhook",
    amountMinor: 500_000,
    currency: "NGN",
    reference: "test-payment-001"
  }
];
```

`500_000` is ₦5,000 when NGN is represented with two decimal places: 100 kobo
is one naira. The reference must already exist in your isolated application
database and must be recognizable by your webhook handler. For repeated runs,
prefer `createPayment` so every run receives a fresh record.

## What the test sends

The Bachs adapter creates one local `collection.succeeded` event. The core
serializes that same event twice and sends two POST requests to your webhook.
The adapter does not call Bachs or create a checkout. The two requests are
deliberately about delivery behavior, not live settlement.

## A runnable repository example

The repository's reference wallet exposes its in-memory store so a test can
verify state without adding a production inspection route. This is a complete
shape for an in-process Vitest test; it uses the reference wallet's actual
exports and the same checkpoint used by its integration tests:

```ts
import { createServer } from "node:http";
import { afterEach, describe, expect, it } from "vitest";
import { BachsProof } from "@bachsproof/core";
import { bachsAdapter } from "@bachsproof/bachs";
import {
  createReferenceWallet,
  InMemoryWalletStore
} from "../apps/reference-wallet/src/index.js";

describe("reference wallet", () => {
  const resources: Array<() => Promise<void>> = [];

  afterEach(async () => {
    while (resources.length > 0) await resources.pop()?.();
  });

  it("reports one credit for a duplicate delivery", async () => {
    const store = new InMemoryWalletStore();
    const wallet = await createReferenceWallet({
      mode: "corrected",
      store,
      testEnvironment: true
    });
    const server = createServer(wallet.app);
    await new Promise<void>((resolve) => server.listen(0, "127.0.0.1", resolve));
    const address = server.address();
    if (!address || typeof address === "string") throw new Error("wallet did not start");
    const url = `http://127.0.0.1:${address.port}`;

    resources.push(async () => {
      await new Promise<void>((resolve, reject) =>
        server.close((error) => error ? reject(error) : resolve())
      );
      await wallet.close();
    });

    const proof = new BachsProof({
      provider: bachsAdapter({ mode: "mock" }),
      target: { baseUrl: url, webhookPath: "/webhooks/bachs" },
      verify: (reference) => store.inspect(reference),
      checkpoint: { name: "after-idempotency-check", timeoutMs: 500 },
      financialVerification: { completionDeadlineMs: 500, pollIntervalMs: 5 }
    });

    const result = await proof.run({
      scenario: "concurrent-duplicate-credit",
      reference: "PAY-FIRST-001",
      amountMinor: 500_000,
      currency: "NGN"
    });

    expect(result.passed).toBe(true);
    expect(result.report.observed?.creditCount).toBe(1);
    expect(result.report.observed?.creditedAmountMinor).toBe(500_000);
  });
});
```

`createReferenceWallet` creates the application, `InMemoryWalletStore` is the
test store, `createServer` gives the app a real HTTP address, and `store.inspect`
is the test-side `verify` callback. These are reference-wallet helpers, not
BachsProof functions. The corrected handler is expected to pass; change
`mode: "corrected"` to `mode: "vulnerable"` and the same controlled run should
fail with two committed credits and `INV-001`.

Run the repository reproduction with:

```bash
pnpm exec vitest run apps/reference-wallet/tests/wallet.integration.test.ts
```

The PostgreSQL reproduction is separate and requires an explicitly supplied
`DATABASE_URL`:

```bash
pnpm exec vitest run apps/reference-wallet/tests/wallet.postgres.integration.test.ts
```

The PostgreSQL file is skipped when that variable is absent; a skipped test is
not evidence of a database result.

## What a pass means

With `verify` configured, a pass means:

- both webhook deliveries matched their expected HTTP behavior;
- the callback returned state for the requested reference;
- the application reported one credit;
- the credited amount and currency matched the expected payment; and
- no financial invariant was violated.

Without `verify`, a pass only describes the delivery outcome. It does not prove
that a database row or ledger entry was committed.

## What a failure tells you

Read the report in this order:

1. `deliveries`: did the request reach the right route and return the expected
   status?
2. `errors`: did preparation, signing, parsing, or delivery fail?
3. `observed`: what did the verifier actually read?
4. `verification.violations`: which rule did that observation break?

you are ready to run the full suite.
