---
title: "Vitest and Jest integration"
description: "Add BachsProof payment correctness checks to an existing test suite."
---

BachsProof is a test engine, not a replacement for Vitest or Jest. Let the host
framework manage the server, database, fixtures, setup, teardown, and ordinary
assertions. Add BachsProof when the test needs payment-specific event schedules
and verification of committed financial state.

## Why the comparison matters

A conventional sequential test can prove that one webhook and a later duplicate
both return successfully:

```ts
const first = await postWebhook(event);
const second = await postWebhook(event);

expect(first.status).toBe(200);
expect(second.status).toBe(200);
expect(await wallet.creditCount(reference)).toBe(1);
```

That test is useful, but it does not arrange the overlapping read/write
interleaving that a race requires. A concurrent application test does:

```ts
const [first, second] = await Promise.all([
  postWebhook(event),
  postWebhook(event)
]);

expect(first.status).toBe(200);
expect(second.status).toBe(200);
expect(await wallet.creditCount(reference)).toBe(1);
```

The checked-in reference-wallet experiment makes this comparison reproducible:

```bash
pnpm exec vitest run apps/reference-wallet/tests/wallet.integration.test.ts
```

Its controlled schedule produces two committed credits and `INV-001` for the
vulnerable handler, and one committed credit for the corrected handler. The
sequential duplicate and replay checks pass. These are local, synthetic events
against the reference wallet; they are not live Bachs payment or settlement
results.

## Vitest

```ts
import { describe, expect, it } from "vitest";
import { BachsProof } from "@bachsproof/core";
import { bachsAdapter } from "@bachsproof/bachs";

describe("wallet webhooks", () => {
  it("keeps a ₦5,000 payment idempotent", async () => {
    const wallet = await startTestApplication({ mode: "corrected" });
    const reference = await wallet.createPayment({ amountMinor: 500_000, currency: "NGN" });
    const runner = new BachsProof({
      provider: bachsAdapter({ mode: "mock" }),
      target: { baseUrl: wallet.baseUrl, webhookPath: "/webhooks/bachs" },
      verify: (paymentReference) => wallet.inspect(paymentReference)
    });

    const result = await runner.run({
      scenario: "concurrent-duplicate-credit",
      reference,
      amountMinor: 500_000,
      currency: "NGN",
      concurrency: 2
    });

    expect(result.passed).toBe(true);
    expect(result.report.financiallyVerified).toBe(true);
    await wallet.close();
  });
});
```

The `startTestApplication`, `createPayment`, and `inspect` helpers belong to
your application test harness. Keep cleanup in `afterEach`/`afterAll` when a
suite has more than one test.

## Jest

The same runner works in Jest because it returns ordinary promises:

```ts
test("rejects an underpaid deposit", async () => {
  const result = await runner.run({
    scenario: "underpaid-payment",
    reference: await createIsolatedPayment(),
    amountMinor: 500_000,
    currency: "NGN"
  });

  expect(result.passed).toBe(true);
  expect(result.report.verification?.violations).toEqual([]);
});
```

Close the application, database, queue worker, and any checkpoint controller
that your test harness created. BachsProof does not reset those resources.

## What integrates programmatically

The host framework still owns test lifecycle and assertions. BachsProof provides
the payment-specific runner, provider adapter, concurrent delivery schedule,
bounded verification polling, and financial report. The `verify` callback is the
explicit application-side bridge: it must return observed state from your own
schema rather than expected values copied from the scenario.
