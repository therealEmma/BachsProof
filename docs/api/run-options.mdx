---
title: "Scenario run options"
description: "Choose the scenario, payment reference, amount, and delivery behavior."
---

Pass these options to `BachsProof.run()` or put the equivalent values in a CLI
test definition. The smallest real-payment run looks like this:

```ts
await runner.run({
  scenario: "sequential-duplicate-webhook",
  reference: "payment-created-in-your-test-database",
  amountMinor: 500_000,
  currency: "NGN"
});
```

`500_000` is 500,000 kobo, or ₦5,000. Use integer minor units. Do not use a
floating-point value such as `5000.00`.

| Field | Type | Required | What it controls |
| --- | --- | --- | --- |
| `scenario` | `ScenarioName` | Yes | One of the 15 implemented payment situations |
| `amountMinor` | `number` | No | Integer test amount; the Bachs fixture default is `5_000_000` |
| `currency` | `string` | No | Three-letter currency; the Bachs default is `NGN` |
| `reference` | `string` | For one-payment real runs unless prepared | Payment reference your webhook understands |
| `references` | `string[]` | For manual unique-payment runs | One distinct reference per participant |
| `concurrency` | `number` | No | Number of overlapping participants; duplicate/unique default to 2 |
| `syntheticReferences` | `boolean` | No | Explicitly use local fixture references; not financial evidence |
| `expectedStatus` | `number`, `number[]`, `"2xx"`, `"4xx"`, `"5xx"` | No | HTTP result the application is expected to return |
| `delayMs` | `number` | No | Delay before the valid event in delayed confirmation |
| `seed` | `string` | No | Replay and debugging label; it does not control OS scheduling |
| `replay` | `BachsProofReport` | No | Reuse the structured event plan from an earlier report |

## References

`concurrent-unique-payments` uses `references`, with one distinct value per
participant. Other one-payment scenarios use `reference`. A configured
`createPayment()` callback can supply missing references automatically.

Explicit references take priority over automatic preparation. If BachsProof has
no reference, callback, or explicit synthetic opt-in, it returns a setup failure
and sends no webhook.

## Expected HTTP status

Most eligible events expect 2xx. Signature and malformed-body scenarios usually
expect 4xx. Use `expectedStatus` when your documented route contract uses a
different status. HTTP status and financial state are checked separately.
