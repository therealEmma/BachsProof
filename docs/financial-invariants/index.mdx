---
title: "Financial invariants"
description: "The rules BachsProof applies to independently observed application state."
---

An invariant is a rule that should remain true after a payment event is
processed. BachsProof evaluates the state returned by your `verify` callback. It
does not inspect a database by itself and does not require a particular schema.

Scenarios describe the input pattern; invariants describe the financial result.
For example, `sequential-duplicate-webhook` and
`concurrent-duplicate-credit` send different delivery schedules, but both can
exercise `INV-001` if two credits are committed. `invalid-webhook-signature`
and `underpaid-payment` send different ineligible events, but both can exercise
`INV-004` if the application credits them.

For the recurring example, an eligible NGN ₦5,000 payment has expected state
`creditCount: 1` and `creditedAmountMinor: 500_000`. An ineligible event has
expected credit count zero.

| ID | Name | Everyday rule |
| --- | --- | --- |
| `INV-001` | Unique Credit | One eligible payment creates at most one credit |
| `INV-002` | Amount Integrity | If a credit exists, its aggregate amount and currency match |
| `INV-003` | Completion | An eligible payment receives its expected credit |
| `INV-004` | No Unexpected Credit | An ineligible payment creates no credit |
| `INV-005` | Aggregate Integrity | An eligible payment's total is correct when the expected count is present |

<Warning>
Expected state comes from the provider adapter. It is not a substitute for
`verify`. A run without an independent state read is financially unverified.
</Warning>

The implementation evaluates all applicable rules and keeps all violations so
one report can show the complete failure. See each page below for a passing
observation, a failing observation, and the exact condition in
`packages/core/src/invariants.ts`.
