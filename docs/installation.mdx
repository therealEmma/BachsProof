title: "Installation"
description: "Install BachsProof in an independent application repository."
---

BachsProof is installed in the application repository that owns the webhook you
want to test. It does not need to be part of the BachsProof source repository.

The commands below use the intended package names and version `1.1.0`. They are
the correct commands once the new namespace has been published to the registry;
this repository does not publish packages automatically. If the registry does
not yet contain `@bachsproof/cli@1.1.0`, use a packed tarball or a workspace
checkout instead of assuming that `npx` can download it.

<CodeGroup>

```bash npm
npm install --save-dev @bachsproof/cli@1.1.0
```

```bash pnpm
pnpm add -D @bachsproof/cli@1.1.0
```

```bash yarn
yarn add --dev @bachsproof/cli@1.1.0
```

</CodeGroup>

## Which package should I install?

The four BachsProof packages are released together at version `1.1.0`:

| Package | Install it when | Responsibility |
| --- | --- | --- |
| `@bachsproof/cli` | You want the normal command-line workflow | Loads config, runs named tests, prints summaries, and returns an exit status |
| `@bachsproof/core` | You want to call BachsProof from Vitest, Jest, or your own runner | Sends deliveries, polls verification, evaluates invariants, and builds reports |
| `@bachsproof/bachs` | You use the built-in Bachs-shaped provider adapter | Creates fixtures, scenario plans, signatures, and exact money conversions |
| `@bachsproof/sdk` | You need a repeatable application-level race | Adds optional test-only request checkpoints |

Most developers need only `@bachsproof/cli`. The CLI depends on the core and
Bachs packages. Install `@bachsproof/core` and `@bachsproof/bachs` directly for a
programmatic runner. Add `@bachsproof/sdk` only when the optional checkpoint
workflow is useful.

The built-in Bachs adapter is explicitly `mode: "mock"`. It creates local,
documented-shaped webhook bodies; it does not need a Bachs API key and does not
call Bachs.

## Runtime requirements

- Node.js 22 or later.
- An application running in an isolated test environment.
- A reachable webhook URL.
- Either a test-side payment preparation function or explicit application
  references for scenarios that need payments.
- A test-side verifier if you want committed financial correctness checks.

## Initialize the files

```bash
npx bachsproof init
```

`bachsproof init` creates four files:

- `bachsproof.config.mjs`: imports the adapter and test list, sets the target
  URL/path and optional signing, and connects the callbacks;
- `tests/bachsproof.test.mjs`: exports the 15 named scenario definitions and
  their amounts, currencies, references, and expected HTTP statuses;
- `tests/bachsproof.setup.mjs`: contains the application-specific
  `createPayment` function that creates an isolated record and returns its
  reference;
- `tests/bachsproof.verify.mjs`: contains the application-specific `verify`
  function that reads committed credits or ledger entries.

The last two callbacks intentionally throw until you connect them to your own
test data. This prevents a delivery-only run from looking like a financial
verification pass. The generated suite uses real application references by
default. Synthetic references are an explicit fixture-only opt-in. The config
imports the test list; the test list does not import the config, so the same
scenarios can be selected by the CLI without circular setup.

`bachsproof init` refuses to overwrite an existing file. Use
`bachsproof init --force` only when replacing those files is intentional.
