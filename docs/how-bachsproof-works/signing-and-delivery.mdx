description: "Learn how BachsProof signs raw test bodies and sends them to your route."
---

When `signing.type` is `"bachs"`, `@bachsproof/cli` wraps the adapter and signs
the exact body that will be sent. The helper in `packages/bachs/src/signing.ts`
creates the test V2 header with HMAC-SHA256:

```text
payload = timestamp + "." + raw_body
signature = HMAC-SHA256(secret, payload)
header = X-Bachs-Signature-V2: t=<timestamp>,v1=<signature>
```

The application must verify the original raw request body before JSON parsing.
The official Bachs Node SDK's `webhooks.constructEvent` helper performs provider
verification and timestamp checks. It does not deduplicate events or apply
business rules; your application still owns those decisions.

## What the core sends

`BachsProof.deliver` sends:

- `POST` to `new URL(webhookPath, baseUrl)`;
- `content-type: application/json`;
- configured target headers;
- provider headers and the configured Bachs signature;
- optional checkpoint headers in controlled mode;
- the serialized event body, or a scenario-specific malformed/tampered body.

It records status, response body, event ID, event type, participant ID, timing,
expected status, and delivery errors. It does not retry a failed HTTP delivery
on behalf of the scenario. A configured `expectedStatus` can accept one status,
an array, or a whole class such as `"4xx"`.

<Warning>
The test signing secret is not a Bachs API key. Keep it in the isolated test
environment and never use a production webhook secret in local examples.
</Warning>
