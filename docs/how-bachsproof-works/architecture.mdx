BachsProof has one simple boundary: BachsProof creates test input and reads the
result; your application decides how to authenticate, store, queue, and credit
payments. The package split keeps that responsibility clear.

```mermaid
flowchart LR
  Config[Config and test names] --> CLI[@bachsproof/cli]
  Tests[15 test scenarios] --> CLI
  CLI --> Core[@bachsproof/core]
  CLI --> Adapter[@bachsproof/bachs]
  Adapter -->|Bachs-shaped fixtures| Core
  Core -->|payment preparation| Prep[Your test setup]
  Core -->|HTTP webhook delivery| App[Your isolated application]
  App --> DB[(Your test database)]
  App -. optional checkpoint call .-> SDK[@bachsproof/sdk]
  Core -. local race controller .-> SDK
  Verify[Your verify callback] -->|committed state| Core
  Verify --> DB
  Core --> Invariants[Five financial invariants]
  Invariants --> Report[Report and CLI exit code]
```

The arrows show package calls and test communication, not a production payment
flow. The core sends the webhook over HTTP. The callback reads your test data.
The optional checkpoint path uses a small local controller, so the application
can run in a separate process.

| Package | Talks to | Main job |
| --- | --- | --- |
| `@bachsproof/cli` | Your config, the core, and the terminal | Creates starter files, loads config, selects tests, and prints the result |
| `@bachsproof/core` | The adapter, your webhook, your callback, and the checkpoint controller | Runs the test and applies the financial rules |
| `@bachsproof/bachs` | The core | Creates Bachs-shaped local events, signatures, money conversions, and scenario plans |
| `@bachsproof/sdk` | Your application and the local controller | Lets selected test requests pause at a named application point |

The CLI is the normal front door. It uses the core and Bachs adapter for you.
The programmatic API can call the core directly. The SDK is separate because
most applications need no application code changes at all.

## The four packages

### `@bachsproof/core`

**In simple English:** the provider-neutral test engine. It validates run
options, chooses references, creates delivery schedules, sends HTTP requests,
polls the verifier, evaluates the five financial rules, and builds the report.

**Why it exists:** the same delivery, polling, reporting, and invariant logic
should work even if another adapter is added later. Without it, the Bachs
adapter would need to duplicate orchestration and every provider would produce
different reports.

**How it communicates:** the CLI constructs `new BachsProof({ ... })`. The core
calls the adapter's `createPayment`, `createScenario`, `serialize`, and
`expectedState` functions. It sends the serialized body to the application's
`target.baseUrl + target.webhookPath`. After delivery, it calls the developer's
`verify(reference, context)` callback and evaluates the returned observation.

**Install it directly?** Not for the normal CLI workflow. Install it directly
when calling `BachsProof` from Vitest, Jest, or another runner.

**Important files and functions:**

- `packages/core/src/orchestrator.ts`: `BachsProof.run`, `deliver`,
  `inspect`, `runScenarioPlan`, and `settleConcurrentDeliveries`.
- `packages/core/src/preparation.ts`: `preparePaymentReferences` and the
  `createPayment` callback bridge.
- `packages/core/src/verification.ts`: `normalizeCallbackState` and
  `verifyWithCallback`.
- `packages/core/src/invariants.ts`: `verifyPaymentState`.
- `packages/core/src/race-controller.ts`: the optional HTTP barrier.
- `packages/core/src/types.ts`: `ProviderAdapter`, `RunOptions`, callback
  contracts, reports, and normalized state.

### `@bachsproof/bachs`

**In simple English:** the Bachs-shaped input generator. It creates local event
objects, serializes the documented envelope, builds the 15 scenario plans,
parses money exactly, and creates test signatures.

**Why it exists:** the core should not know Bachs field names such as
`collection.succeeded`, `checkout.expired`, or `amount_paid`. Without this
package, provider details would leak into the generic engine and make the core
hard to reuse.

**How it communicates:** `bachsAdapter()` returns the `ProviderAdapter` object
that the core consumes. The CLI adds `signBachsWebhook` when a signing secret is
configured. The adapter returns normalized expected state to the core; it does
not call Bachs or create a live checkout.

**Install it directly?** Usually no. `@bachsproof/cli` uses it for the normal
configuration. Install it directly when building a programmatic runner or
working with Bachs event fixtures.

**Important files and functions:**

- `packages/bachs/src/adapter.ts`: `bachsAdapter` and the explicit `mode:
  "mock"` boundary.
- `packages/bachs/src/fixtures.ts`: `createBachsMockFixture`,
  `createBachsScenario`, `serializeBachsPaymentEvent`,
  `parseBachsWebhookEvent`, `normalizeBachsWebhookEvent`, and
  `expectedBachsState`.
- `packages/bachs/src/money.ts`: decimal-string and minor-unit conversions.
- `packages/bachs/src/signing.ts`: `signBachsWebhook`.

### `@bachsproof/cli`

**In simple English:** the command-line front door. It loads
`bachsproof.config.mjs`, selects named tests, prepares signing, runs the core,
prints summaries, and returns exit code `0` or `1`.

**Why it exists:** developers need a repeatable command that works from an
application repository. Without it, every team would need to write its own
config loader, scenario loop, signing composition, and report printer.

**How it communicates:** `main` parses `init` or `test`; `loadConfig` imports
the config; `runConfig` creates one core runner per selected test and passes the
configured adapter, target, callbacks, and options to it. `initProject` writes
the four starter files.

**Install it directly?** Yes, for the documented workflow. It is the package
that supplies the `bachsproof` executable and the `defineConfig` and
`bachsAdapter` convenience exports.

**Important files and functions:**

- `packages/cli/src/cli.ts`: `main`, argument parsing, and terminal output.
- `packages/cli/src/runner.ts`: `loadConfig`, `runConfig`,
  `withBachsSigning`, and `summarizeRuns`.
- `packages/cli/src/init.ts`: `initProject` and the generated templates.
- `packages/cli/src/config.ts`: `defineConfig`.
- `packages/cli/src/types.ts`: CLI config and test types.

### `@bachsproof/sdk`

**In simple English:** optional application-side test instrumentation. It lets
two webhook requests stop at a named point, such as immediately after both have
read `PENDING`, so the test can release them together.

**Why it exists:** ordinary HTTP concurrency overlaps requests but cannot promise
that they reach the same application line together. Without the SDK, a race may
be missed because one request finishes before the other reads. The SDK is not a
lock and does not make the database safe.

**How it communicates:** the core's `RaceController` creates a session and
passes controller URL, session ID, participant ID, and token in
`x-bachsproof-*` headers. `checkpointMiddleware` turns those headers into an
`AsyncLocalStorage` context. `checkpoint(name)` sends an authenticated arrival
to the controller and waits until the core calls `release`.

**Install it directly?** Only when you choose controlled concurrency. It is
optional for black-box testing and must not be enabled in production.

It is called an **SDK** (software development kit) because it is a small set of
helpers that application code can import. It does not run the test suite or
own the database; it only lets test requests announce that they reached a
named point in the application.

**Important files and functions:** `packages/sdk/src/checkpoint.ts` contains
`configureCheckpoint`, `checkpointMiddleware`, `checkpoint`,
`runWithCheckpointContext`, `getCheckpointContext`, and the process-wide
enable/disable helpers. The controller it talks to is
`packages/core/src/race-controller.ts`.

## What remains application-owned?

Your application still owns webhook authentication, event persistence, payment
and order matching, amount and currency checks, transaction boundaries,
idempotency, worker queues, database cleanup, and production deployment.
BachsProof does not add a route or inspect your database automatically. The
`verify` callback is the narrow test-side bridge that reads your committed
records and returns counts, integer amounts, currency, and optional ledger
entries.

<Note>
The reference wallet in `apps/reference-wallet` is an application used to
demonstrate this boundary. It is not a fifth BachsProof package.
</Note>
