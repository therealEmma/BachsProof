title: "Payment event generation"
description: "Understand what the provider adapter creates and what stays synthetic."
---

The Bachs adapter uses `mode: "mock"`. It generates local webhook envelopes
with the documented event names and the fields needed by the current scenarios.
It does not call a Bachs API, create a checkout, retrieve a payment, or settle
money.

## Provider body versus core fields

The serialized wire body contains only the provider envelope:

```json
{
  "id": "evt_example",
  "type": "collection.succeeded",
  "created_at": "2026-01-01T00:00:00.000Z",
  "organization_id": "acct_bachsproof_test",
  "data": {
    "charge_id": "ch_example",
    "checkout_id": "chk_example",
    "reference": "wallet-deposit-001",
    "status": "SUCCEEDED",
    "amount": "5000.00",
    "currency": "NGN"
  }
}
```

The adapter also keeps normalized fields such as `reference`, `amountMinor`,
`eligible`, and `providerPaymentId` on its in-memory event object. Those fields
are used by the provider-neutral core and are deliberately not added to the
wire body. This keeps the application test close to the provider envelope.

`createBachsMockFixture` creates a successful `collection.succeeded` event.
`createBachsScenario` adds lifecycle, malformed-body, signature, amount,
currency, underpaid, and failed-payment plans. `serializeBachsPaymentEvent`
keeps only the envelope. These functions live in
`packages/bachs/src/fixtures.ts`.

See [Bachs events](/bachs/events) for the event families and their boundaries.
