---
title: "Test reports"
description: "Read the structured evidence BachsProof records for every run."
---

Each run returns a `BachsProofResult` containing `passed` and a structured
`BachsProofReport`. The report is designed for debugging and replay, not only for
a green/red status.

Read it as a story: what BachsProof sent, how the application responded, what
your callback saw in the database, and which money rule passed or failed.

## What the report tells you

- `scenario`, `provider`, and `mode` identify what ran;
- `event` and `expected` describe the primary synthetic input and comparison;
- `observed` contains the first callback result when verification ran;
- `payments` contains per-reference results for concurrent unique payments;
- `verificationMode` is `callback` or `none`;
- `financiallyVerified` tells you whether committed state was inspected;
- `deliveries` contains each HTTP request, status, response body, and error;
- `checkpoints` contains `arrival`, `release`, and `abort` traces;
- `errors` contains preparation, delivery, configuration, and invariant errors;
- `replay` contains seed, concurrency, checkpoint name, controlled flag, and a
  limitation note;
- `startedAt` and `completedAt` record run timing.

## Reading a result correctly

`passed: true` can coexist with `financiallyVerified: false` when no verifier
was configured. That means only that the expected deliveries succeeded. A
financially verified pass requires the callback state and applicable invariants
to pass as well.

The CLI prints a compact summary and supports `--json` for CI artifacts. A
programmatic test can call `writeReport` from `@bachsproof/core`; it creates the
parent directory and writes formatted JSON. The report stores the structured
event object, not the exact raw serialized body or every request header, so a
replay does not claim byte-for-byte provider delivery.
