---
title: "Idempotency"
description: "Why a payment operation must be safe to repeat."
---

Idempotency means that repeating the same logical operation does not create a
second financial effect. If a customer pays ₦5,000 once and the provider sends
“payment `pay-123` succeeded” twice, the application may record both delivery
attempts but must create at most one ₦5,000 credit.

Idempotency and financial correctness are related, but they are not the same:

- **Idempotency:** repeating one operation is safe. It mainly protects against
  duplicates.
- **Financial correctness:** the final saved result has the right count, amount,
  currency, eligibility, and completion state.

An application can be idempotent and still be wrong. For example, it might
save one credit for **₦4,999** instead of one credit for **₦5,000**, or save one
credit for an expired payment. BachsProof checks both the “only once” rule and
the wider financial result.

## A durable pattern

Use an identity tied to the business operation, enforce it in the database, and
make the state change atomic:

```text
begin transaction
  authenticate event
  insert event identity if new
  insert credit with unique payment idempotency key
  update wallet balance
  mark payment completed
commit
```

The exact schema is yours. BachsProof checks the observable result with
`INV-001`, rather than requiring a particular ORM. Event IDs are useful for
deduplicating one delivery; a local payment reference or business idempotency
key is usually the stronger identity for “this financial payment may credit
once.”

<Warning>
An in-memory “already seen” set is not enough when multiple processes or
workers can handle webhooks. The durable boundary must match your deployment.
</Warning>
