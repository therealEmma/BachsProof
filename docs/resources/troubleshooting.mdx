---
title: "Troubleshooting"
description: "Fix common BachsProof configuration, delivery, and verification failures."
---

Start with the layer that failed: preparation, HTTP delivery, or financial
verification. A green HTTP response does not override a red financial check.

## “Real application reference is required”

Implement `createPayment`, add a real `reference`/`references` value, or
intentionally set `syntheticReferences: true` for a fixture-only run.

## “Payment preparation failed”

Check that the application created a fresh record, returned a non-empty string,
and did not reuse a reference from another selected scenario. For the unique
payments scenario, return one distinct reference per participant.

## HTTP connection, 404, or 401

Check `baseUrl`, `webhookPath`, the running process, and whether the route is
available in the test environment. For signed events, confirm the secret and
that the route captures raw bytes before verification.

## Expected 4xx did not occur

Confirm `expectedStatus` is configured for the deliberately rejected scenario.
For tampered, invalid-signature, and malformed-body tests, a 4xx is the normal
generated expectation. A 2xx may mean the application accepted an event it was
supposed to reject.

## Financial verification status messages

The CLI uses the existing report fields to distinguish these cases:

- **Financial verification not configured** — no `verify` callback is enabled;
  the result is delivery-only.
- **Financial verification configured; did not run** — preparation or run setup
  stopped before BachsProof could call the callback.
- **Financial verification attempted; could not complete** — the callback timed
  out, threw, or returned a value that failed runtime validation.
- **Financial verification completed** — committed state was read and the
  invariants passed.
- **Financial verification completed; financial violations detected** — state
  was read, but one or more invariant rules failed.

Import and enable `verify`. Set `requireFinancialVerification: true` when CI
must refuse an unverified run.

## Verifier timeout

Return `pending: true` while work is in flight, inspect the same test database
used by the worker, and increase the bounded deadline only when the application
needs it. A callback error or malformed value is a real failure, not a pending
state.

If the callback returns inaccurate data, check that it reads the same isolated
database used by the webhook worker and filters by the requested reference. A
callback that returns expected values instead of committed rows can make a bad
test look good.

If validation reports a path such as `ledgerEntries[0].type`, add the missing
required property. Each ledger entry needs `id`, `type`, and `amountMinor`; the
array itself is optional.

## Separate test data

Use a separate test database or a clearly isolated test schema. BachsProof does
not reset, migrate, or delete application data, and duplicate or negative
scenarios intentionally create unusual inputs. Fresh references and scoped
cleanup prevent one run from changing the next run.

## Duplicate or stale results

Create one fresh payment per selected test, use scoped cleanup, and make sure
the verifier reads committed credits for the requested reference. Do not share
a customer balance between tests unless the test explicitly needs that state.
