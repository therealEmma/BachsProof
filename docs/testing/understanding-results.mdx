---
title: "Understanding results"
description: "Read plain-language financial correctness results."
---

A scenario passes only when payment preparation, webhook delivery, financial
verification, and all applicable financial rules succeed.

```text
BachsProof v2.1.0

Scenario summary
  PASS  Sequential duplicate webhook  38ms
  FAIL  Concurrent duplicate credit  42ms

Failure details

FAIL  Concurrent duplicate credit
  Scenario: concurrent-duplicate-credit
  Payment reference: test-payment-123
  Webhook deliveries:
    PASS HTTP 200 collection.succeeded
    PASS HTTP 200 collection.succeeded
  Financial verification: FAIL
  Expected: 1 credit(s), totalling NGN 5,000.00 (500000 minor units) (eligible)
  Observed: 2 credit(s), totalling NGN 10,000.00 (1000000 minor units); currency NGN; status PAID
  Financial invariant violations:
    - INV-001 Unique Credit: Payment test-payment-123 created 2 credits

Final summary
  2 scenario(s): 1 passed, 1 failed
  Financial verification: 2/2 completed
  Financial invariant violations: 1
  Duration: 80ms
```

The example uses representative fixture data; the identifiers and timings are
not from a real payment. For an ineligible scenario, the expected line is
`0 credit(s), totalling NGN 0.00`, not a successful-payment expectation.

Webhook delivery and financial correctness are separate checks. An HTTP `400`,
`503`, or other unexpected response remains a delivery failure; it is never
silently treated as success. BachsProof still verifies financial state when it
can do so safely, so the report may show both a delivery failure and separate
financial evidence. A timeout or missing evidence is reported as unverified,
not as zero credits.

JSON output keeps the invariant identifiers (`INV-001` through `INV-005`) and
the delivery and observed financial evidence for CI diagnostics.

The result describes your application's financial outcome. It is not a report
that the Bachs API accepted a checkout; use the official [Bachs event and
delivery tools](https://docs.bachs.io/developer-portal/events) for provider-side
delivery inspection.
