---
title: "Automatic payment preparation"
description: "Create fresh application records through createPayment(context)."
---

Automatic preparation is the recommended workflow for local and CI runs. In
simple English, BachsProof calls your callback to create the application record
before it sends the synthetic webhook.

## The callback contract

```js
export async function createPayment({
  scenario,
  amountMinor,
  currency,
  paymentIndex,
  paymentCount
}) {
  const payment = await applicationTestApi.createPayment({
    scenario,
    amountMinor,
    currency,
    paymentIndex,
    paymentCount
  });
  if (!payment?.reference) throw new Error("payment API returned no reference");
  return payment.reference;
}
```

`applicationTestApi` is application-specific code. It is not exported by
BachsProof. Replace it with your ORM, repository, test service, fixture, or
test-only endpoint.

| Property | Meaning |
| --- | --- |
| `scenario` | The named scenario currently running. |
| `amountMinor` | The integer amount expected by the scenario. `500_000` NGN is ₦5,000. |
| `currency` | The three-letter currency code. |
| `paymentIndex` | Zero-based payment number within this scenario. |
| `paymentCount` | Total number of payments this scenario requires. |

The callback must create a fresh record and return its non-empty reference. A
reference may be an order ID, invoice ID, deposit ID, or application payment
reference—the value only needs to be the key your webhook handler understands.
For `concurrent-unique-payments`, BachsProof calls the callback once per
participant; return a different reference for each call.

Each prepared payment needs a fresh reference because the application database
may already contain the outcome from an earlier run. Reusing a reference can
make a later scenario observe another test's credit, hide an idempotency bug, or
cause the CLI to reject the selected suite. The CLI tracks references within a
suite and rejects accidental reuse.

## Prisma and PostgreSQL

Prisma is only an example. BachsProof remains database-agnostic and does not add
Prisma to your project. If you use Prisma, pass the dedicated test database URL
explicitly:

```js
import dotenv from "dotenv";
import { PrismaClient } from "@prisma/client";

dotenv.config({ path: process.env.BACHSPROOF_ENV_FILE ?? ".env" });

const databaseUrl = process.env.BACHSPROOF_TEST_DATABASE_URL;
if (!databaseUrl) throw new Error("BACHSPROOF_TEST_DATABASE_URL is required");

export const prisma = new PrismaClient({
  datasources: { db: { url: databaseUrl } }
});
```

The target application and `createPayment`/`verify` callbacks must use this same
isolated URL. In a monorepo, make the root `.env` path explicit or export the
variable before starting both processes. Do not let the callback fall back to a
developer or production `DATABASE_URL`.

Then adapt the callback to your schema:

```js
import { randomUUID } from "node:crypto";
import { prisma } from "./test-support/prisma.mjs";

export async function createPayment({
  scenario,
  amountMinor,
  currency,
  paymentIndex,
  paymentCount
}) {
  const reference = `bachsproof-${scenario}-${paymentIndex}-${randomUUID()}`;
  const payment = await prisma.payment.create({
    data: {
      reference,
      amountMinor: BigInt(amountMinor),
      currency,
      status: "PENDING"
    }
  });
  return payment.reference;
}
```

The same pattern works when the application calls the record a wallet deposit,
order, invoice, or ledger operation. Create the record that the webhook handler
will look up; do not start a live provider charge.

## Choosing a reference method

| Use this | Choose it when | Financial evidence? |
| --- | --- | --- |
| `createPayment` | You want each run to create a fresh record. | Yes, with `verify`. |
| `reference` / `references` | Another test already created isolated records. | Yes, with `verify`. |
| `syntheticReferences: true` | You are testing fixtures, signing, or HTTP behavior only. | No; fixture-only. |

Explicit references take precedence over automatic preparation. Synthetic mode is
an explicit opt-in and must not be presented as a financially verified run.
