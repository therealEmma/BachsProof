---
title: "Automatic payment preparation"
description: "Create fresh application records through createPayment(context)."
---

Automatic preparation is the recommended workflow for repeated local and CI
runs. BachsProof calls your callback only when a selected scenario needs a
reference and the test did not supply one. In simple English, this helper makes
a fresh test payment before the webhook arrives.

```js
export async function createPayment({
  scenario,
  amountMinor,
  currency,
  paymentIndex,
  paymentCount
}) {
  const payment = await applicationTestApi.createPayment({
    label: `bachsproof-${scenario}-${paymentIndex}`,
    amountMinor,
    currency,
    paymentIndex,
    paymentCount
  });
  if (!payment?.reference) throw new Error("payment API returned no reference");
  return payment.reference;
}
```

The function above is application-specific. `applicationTestApi` is not
provided by BachsProof; it might call a test-only endpoint, an application
service, or a database seeder. It must create an order for the requested
amount and return its reference. For the recurring example, `500_000` NGN
minor units represents ₦5,000.

For `concurrent-unique-payments`, BachsProof calls the callback once per
participant. The callback must return different references. BachsProof validates
empty values and the CLI rejects a reference reused by another selected test.
It sends no webhook for a scenario whose preparation failed.

<Warning>
The callback must create test records without charging real instruments or
calling a live financial provider. Use a test API, test service, or isolated
database seeder owned by your application.
</Warning>

## Which reference method should I choose?

| Use this | Choose it when | Financial evidence? |
| --- | --- | --- |
| `createPayment` | You want every run to create a fresh application record | Yes, when paired with `verify` |
| `reference` / `references` | You already created isolated records and know their IDs | Yes, when paired with `verify` |
| `syntheticReferences: true` | You are testing fixture serialization, signing, or a route without a real payment record | No; fixture-only |

Use only one method for a given run. Explicit references take precedence over
automatic preparation, and synthetic mode is an explicit opt-in.
