---
title: "Concurrent webhook testing"
description: "Understand ordinary concurrency and the optional controlled schedule."
---

`concurrent-duplicate-credit` sends the same eligible event to the target in a
delivery wave. The runner uses `Promise.allSettled`, so successes and every
delivery error are retained in the report.

```js
{
  name: "duplicate race",
  scenario: "concurrent-duplicate-credit",
  concurrency: 3,
  reference: "prepared-payment-1"
}
```

This is black-box HTTP concurrency. It exercises the real route but does not
guarantee that two requests read the same database state. A scheduler can let
one request finish before another begins its critical section.

For a repeatable application interleaving, configure the optional checkpoint
mode and place a checkpoint after the application's idempotency read. See
[controlled concurrency](/advanced/controlled-concurrency). Even controlled
mode coordinates only the named application point; the database still needs a
durable unique constraint or equivalent atomic protection.

Think of ordinary concurrency as two runners entering a room at nearly the
same time. Controlled concurrency adds a starting gate: both runners must reach
the named line before either is allowed to continue. The gate makes a test
schedule repeatable; it does not make the application correct for you.
