---
title: "Understanding HTTP expectations"
description: "Configure accepted responses for successful and deliberately rejected events."
---

Every delivery has an HTTP result. A scenario can expect one status, a list of
statuses, or a status class.

```js
{
  name: "invalid signatures are rejected",
  scenario: "invalid-webhook-signature",
  expectedStatus: "4xx",
  reference: "prepared-payment-2"
}
```

Supported values are `400`, `[400, 401]`, `"2xx"`, `"4xx"`, and `"5xx"`.
Without `expectedStatus`, any non-2xx response is a delivery error. With it, a
deliberate rejection can pass the transport part of the test.

BachsProof evaluates HTTP expectation separately from financial verification. An
expected rejection can pass delivery while `verify` confirms zero credits.
Conversely, HTTP `200` can still fail financial correctness if the application
committed the wrong state.
