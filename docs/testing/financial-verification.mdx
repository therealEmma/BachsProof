---
title: "Implementing financial verification"
description: "Read committed state from your own application without production changes."
---

Financial verification is a read from your application's isolated test store.
It is the difference between “the webhook returned 200” and “the application
saved exactly one correct credit.” BachsProof does not know whether your money
lives in wallets, orders, invoices, deposits, or a double-entry ledger, so you
implement the small `verify(reference, context)` bridge.

## The smallest valid response

```js
export async function verify(reference) {
  return {
    reference,
    creditCount: 0,
    creditedAmountMinor: 0,
    currency: "NGN"
  };
}
```

The four fields are required. `status`, `pending`, and `ledgerEntries` are
optional. The example is only the shape; a real callback must query committed
records.

## A complete Prisma/PostgreSQL example

```js
import { prisma } from "./test-support/prisma.mjs";

function toSafeMinorUnits(value) {
  const number = typeof value === "bigint" ? Number(value) : Number(value);
  if (!Number.isSafeInteger(number)) {
    throw new Error("Financial amount exceeds JavaScript safe integer range");
  }
  return number;
}

export async function verify(reference, context) {
  const payment = await prisma.payment.findUnique({ where: { reference } });
  const credits = await prisma.walletCredit.findMany({ where: { reference } });
  const unfinishedWorkerStates = new Set([
    "QUEUED", "WAITING", "PROCESSING", "RETRY_SCHEDULED", "RETRYING"
  ]);

  return {
    reference,
    creditCount: credits.length,
    creditedAmountMinor: credits.reduce(
      (total, credit) => total + toSafeMinorUnits(credit.amountMinor),
      0
    ),
    currency: payment?.currency ?? "NGN",
    status: payment?.status ?? "NOT_FOUND",
    pending: !payment || unfinishedWorkerStates.has(payment.workerStatus),
    ledgerEntries: credits.map((credit) => ({
      id: String(credit.id),
      type: String(credit.type),
      amountMinor: toSafeMinorUnits(credit.amountMinor),
      currency: credit.currency
    }))
  };
}
```

The table and field names are examples. Adapt them to your schema, but keep the
meaning of each returned field:

| Field | Meaning |
| --- | --- |
| `reference` | The exact reference requested by BachsProof. |
| `creditCount` | Count of committed credit records for that reference. |
| `creditedAmountMinor` | Sum of committed integer minor-unit amounts. |
| `currency` | Currency of the observed records. |
| `status` | Optional application status for the report. |
| `pending` | Optional signal that asynchronous work can still change the state. |
| `ledgerEntries` | Optional evidence; each entry needs `id`, `type`, and `amountMinor`, with optional `currency`. |

The runtime schema requires `type` on every supplied ledger entry. An optional
array does not make its entries optional. A missing `type` is reported as an
invalid value at `ledgerEntries[0].type`, with the expected and received types.

## Money and evidence

Amounts are integer minor units. In a two-decimal currency, `500_000` NGN is
₦5,000. Prisma returns PostgreSQL `BIGINT` values as JavaScript `bigint`; use a
safe-integer check before converting them to the `number` required by the
callback contract. Do not read a cached balance or calculate the answer from
the webhook body.

The callback's `context` is useful for diagnostics, but it is not evidence:

- expected state comes from the provider adapter and scenario;
- observed state comes from your committed database or ledger rows;
- invariant evaluation is performed by BachsProof after it receives both.

For an eligible payment, one correct committed credit should report one row and
the expected amount. Two rows or an incorrect aggregate become invariant
violations. For an ineligible payment, a credit is a violation even if the HTTP
route returned success.

## Asynchronous applications

Return the current database observation with `pending: true` while a queued,
waiting, processing, or retrying worker can still write the financial record.
Do not infer this solely from a payment status of `PENDING`; that may be a
business status left behind after a failed worker. Use the application's actual
job state.

```js
financialVerification: {
  completionDeadlineMs: 10_000,
  pollIntervalMs: 25,
  negativeObservationWindowMs: 250
}
```

The completion deadline bounds polling for eligible results. The negative
observation window gives an ineligible result with no credit a short, bounded
chance to reveal a late erroneous write. Neither window proves what a future
job will do after testing ends. See [asynchronous applications](/testing/asynchronous-applications)
for the full timing explanation.
